## Cases
**[ ] 1. L'échange.** `mgmtOrgChanger(m,orgId)` : la partie du joueur **devient** l'organisation `orgId` : (a) la sous-partie `m.orgs[orgId]` devient la partie courante (roster, carte, agenda, finances, classements, hist, calendrier…) ; (b) **l'ancienne organisation du joueur (Split ou l'autre) prend la place dans `m.orgs`** comme sous-partie vivante, avec son état tel qu'il était (rien n'est perdu) ; (c) ce qui appartient au **joueur** reste : son contrat (nouveau : salaire et durée de l'offre), sa mémoire, son carnet, ses prix, ses défis, sa confiance repart d'une valeur neutre, ses suivis (les combattants suivis qui sont dans l'ancienne organisation restent suivis comme combattants extérieurs), ses espoirs qui restent dans l'ancienne organisation deviennent des combattants extérieurs. **Aucune donnée n'est dupliquée ni perdue** : un test compare le multiensemble de combattants avant/après (chaque combattant est dans exactement une organisation).
**[ ] 2. Le chemin du joueur.** L'offre acceptée (écran Ton poste / bilan : le bouton existe, lot 58) déclenche `mgmtOrgChanger` après une **confirmation** (« Tu quittes X pour Y. Ton équipe, ton carnet et ta réputation te suivent ; tes combattants restent chez X. »), puis un écran d'**arrivée** dans la nouvelle organisation : réutilise **l'écran d'arrivée existant** (`mgmt_arrivee`, les 3 étapes ; lis-le) avec le nom, le palmarès, les combattants et ce qui manque (P4) **de la nouvelle organisation** ; les trois espoirs de Leïla sont recalculés pour elle.
**[ ] 3. Les conséquences.** La presse le raconte (une ligne par côté, `relu:false`, spécifique) ; l'ancienne organisation réagit (le patron, la rivalité : le joueur peut devenir la « rivale du moment » de son ancienne organisation si les raisons existent) ; **le calendrier du jeu continue sans saut** ; la sauvegarde reste valide.
**[ ] 4. Sauvegarde et poids.** `MGMT_SAVE_VERSION` ne change pas (clés facultatives) ; la partie neuve ≤ plafond (`tests/mgmtReleveReduit.test.js` en arrière-plan) ; une partie ancienne se charge et joue. Un changement d'organisation sauvegardé se recharge **à l'identique** (même `mgmtSerialiser`).
**[ ] 5. Tests** (`tests/mgmtLot61T1.test.js`, dans `test` ET `test:watch`) : par le chemin réel (`mgmtPasseGenerer('split',{soirees:3})` + `mgmtMondeVivantGenerer` + des soirées jouées) : l'échange conserve les combattants ; aller **Split → autre → Split** rend une partie cohérente ; la partie jouée dans la nouvelle organisation (une soirée complète) ne plante pas ; aucune clé orpheline ; le rechargement est identique ; les empreintes de `tests/mgmtPasse.test.js` ne bougent pas pour une partie sans changement ; déterminisme (jamais `rnd()`).
**[ ] 6. Fin.** `?v=`, versions, lint ; commit final `Monde lot 61 T1 : changer d'organisation` ; compte rendu honnête ; `TOUT_EST_FINI`.
