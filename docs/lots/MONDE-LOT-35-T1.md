## Le constat
Beaucoup de tests recréent la même partie : `setSeed(20261008); mgmtPasseGenerer('split',{soirees:6})` (une vingtaine de secondes), les six ans complets (`soirees:62`, 35 s), puis `mgmtMondeVivantGenerer` (les sept autres organisations : 4 minutes). Chaque `newGameWindow()` repart de zéro, donc chaque test paie. Un `npm run check` dure 15 à 40 minutes, le plus long fichier (~364 s) fixe à lui seul la durée de la suite, et chaque reprise d'un test coûte 20 à 150 s.

## 1. Le cache (`tests/helpers/partieCache.js`, branché dans `tests/helpers/loadGame.js`)
- Dans `newGameWindow`, après le chargement des scripts du jeu, **enrobe** `window.mgmtPasseGenerer` et `window.mgmtMondeVivantGenerer` (garde les fonctions d'origine : `orig`). Si la variable d'environnement `CL_TEST_CACHE=0`, n'enrobe rien.
- Clé de cache = empreinte SHA-1 de : le contenu de **tous les fichiers** `.js` listés par `index.html` (lis-les comme `readScriptOrder()`), l'appelant (`'passe'` ou `'monde'`), les arguments sérialisés (`orgId`, `opts`), et l'**état de la RNG au moment de l'appel** (`SEED`, lue dans la fenêtre). Toute modification du code du jeu change donc la clé : jamais de résultat périmé.
- Premier appel (cache vide) : appelle `orig`, puis écrit `{partie: JSON.stringify(m), seedApres: SEED, ...}` dans `os.tmpdir()/cage-legacy-cache-tests/<empreinte>.json` (écriture atomique : fichier temporaire puis `rename`). Appels suivants (même processus ou autre fichier de test, même relance) : lit le fichier, **restitue exactement les effets** de la fonction d'origine : `m = JSON.parse(...)` rendu à l'appelant, **`G.mgmt` posé comme l'original le fait**, **`SEED` remise à `seedApres`**, et tout autre global que la fonction d'origine modifie (cherche-les : `grep` dans `mgmt-passe.js`, `mgmt-predecesseur.js`, `mgmt-monde*.js` ; les tables de visites, les compteurs d'identifiants, `G.theme`…). Un cache en mémoire du processus (Map) évite de relire le disque.
- Les parties se rendent **au format JSON** : tout ce que `JSON.stringify` perd (Map, Set, fonctions, `undefined`) doit déjà être absent de la partie, sinon la sauvegarde du jeu ne marcherait pas non plus ; vérifie-le dans le test ci-dessous, et si un champ se perd, ne mets pas cette fonction en cache (replie sur `orig`).
- Protège contre la course (deux processus qui génèrent la même clé en même temps) : chacun génère puis `rename` atomique ; le dernier gagne ; aucun fichier à moitié écrit n'est lu (un JSON illisible est ignoré et régénéré).
- Nettoyage : au démarrage, supprime les fichiers du cache de plus de 7 jours ; plafond de 2 Go (supprime les plus anciens).

## 2. La preuve que le cache est transparent (nouveau `tests/partieCache.test.js`, à inscrire dans `test` ET `test:watch` de `package.json`)
(1) Pour `mgmtPasseGenerer('split',{soirees:3})` à la graine 20261008 et pour `mgmtMondeVivantGenerer` sur une petite partie (2 soirées) : le résultat **avec cache vide** (`CL_TEST_CACHE=0`), puis **au premier appel avec cache** (qui écrit), puis **au second appel** (qui lit) donnent le **même JSON** (`JSON.stringify` égal), la **même `SEED` après**, et les **100 tirages suivants de `rnd()` sont identiques** ; `G.mgmt` est la même partie. (2) Une modification du code (simule-la en changeant la clé : un argument ou un octet du contenu) donne une autre empreinte et régénère. (3) Un fichier de cache corrompu (tronqué) est ignoré. (4) Mesure : le second appel de `mgmtPasseGenerer(…{soirees:6})` dure moins de 1,5 s ; écris les temps dans le compte rendu.
